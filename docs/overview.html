01 · Purpose & Scope

Comfort-first universal AI CLI without command memorization

UCLI is a planned universal command-line interface designed so its owner can open a terminal, describe work in plain language, observe live progress, adjust model, account or effort through visible controls, and resume cleanly after interruptions. As of October 17, 2026, the project is in planning only: no UCLI runtime, benchmark harness, or human usability study has been executed yet.

Development targets a separate local repository at USER_HOME/Downloads/Projects/ucli while keeping the existing cly toolset untouched and usable. Authoritative specifications reside in docs/implementation-plan.md, docs/experience.md, docs/architecture.md, docs/contracts.md, docs/provider-integrations.md, docs/verification.md, and planning/backlog.json.

02 · Everyday Experience

One command registry across prompt, CLI flags, and scripts

Whether starting an interactive home session or running a single non-interactive command, UCLI resolves intent through one shared command registry. Interactive prompts, --help output, and shell completions are generated from the same definitions so interactive controls and scripts never drift apart. 

# Proposed illustrative commands (not yet installed)
ucli                              # Open interactive home with visible controls
ucli run "Fix the failing tests"  # Start a managed task from plain language
ucli models                       # Inspect admitted models, runtimes & capabilities
ucli tasks                        # View active, blocked, or resumable tasks

The interactive home (`P11`) is intentionally small: it preserves native terminal scrollback and in-progress user input while keeping the active model, account connection, effort level, and task status visible and switchable via keyboard shortcuts. Early native passthrough (`P10`, `P14`) ensures provider-specific features remain accessible in Phase 1 without waiting for UCLI wrappers, while `P27` later hardens native escape handling and adds an optional read-only `cly` import preview.

03 · Architecture

Local Go core, typed domain separation, and verified adapters

The recommended core is a local Go binary (`P01`, provisional until packaged cross-platform process and terminal spikes pass), paired with local SQLite state (`P08`), native OS process and credential adapters (`P09`, `P15`), an optional background supervisor for persistent work (`P20`), and versioned runtime adapters.

UCLI keeps model, runtime, account, task, and preset strictly separate in one typed effective-setting resolver (`P07`). Codex app-server (`OAI-01`) is the first structured runtime candidate (`P02`, `P12`). Antigravity (`agy`) (`AGY-01`) is the conditional second candidate (`P03`, `P13`), pending lifecycle and concurrent account-isolation proof (`P04`), with Meta Muse Code (`MUS-01`) or an authorized Claude API path (`CLA-01`) as fallbacks. Structured capabilities must be proven against exact executable builds—never inferred from catalog listings. A public adapter extension kit (`P25`) is deferred until two real production adapters are running.

04 · Accounts & Automatic Routing

Isolated local credentials and explainable two-stage routing

Local work requires no cloud account. Optional GitHub sign-in in Phase 4 (`P28`, `GIT-01`) syncs device identity, user preferences, and non-secret connection metadata—it never grants provider model entitlement. Provider credentials remain local by default in OS secret stores with verified isolated binding (`P04`, `P15`). UCLI never rewrites or swaps the user's active shared native login to run or switch a UCLI task.

Automatic routing (`P18`) operates in two inspectable stages:

  1. Deterministic constraint filter: Enforces authorized account, model availability, tool permissions, data boundary, and budget rules. Default auto for model or effort never widens account or provider boundaries.
  2. Eligible route ranking: Orders surviving candidates by task quality fit, latency, and observed quota capacity. An optional bounded decision model (`P24`) comes later and cannot broaden authority.

Quota tracking (`P17`) treats unknown quota as distinct from both zero and unlimited: when a pool has no known exhaustion but lacks a verified remaining balance, UCLI permits at most one conservative in-flight task per authorized pool. Shared pools and reset timestamps record explicit provenance, and a crashed or canceled local worker never assumes upstream work stopped or frees its quota reservation until confirmed.

05 · Workflow & Recovery

Durable task records, reconciliation, and explicit handoff packets

Every task persists durable SQLite records across attempts, streamed events, and output artifacts (`P08`). Task attempts terminate or pause in explicit states: completed, blocked, failed, unknown, or interrupted. When an interruption occurs after uncertain external side effects, retrying requires explicit state reconciliation (`P23`) rather than blind re-dispatch.

Multi-agent workflows (`P21`, `P22`) coordinate small dependency graphs with automated verification checks, isolated file-editing ownership, and explicit context packets. Switching models or runtimes mid-workflow transfers structured context packets and verified artifacts—never pretending private model memory is portable across providers.

06 · Delivery Phases & Kickoff Order

Five gated phases backed by consuming paths and failure evidence

Delivery progresses through five phases gated by milestones G0–G4 (`docs/implementation-plan.md`, `docs/verification.md`). Every gate requires working consuming paths and negative/failure-boundary evidence. Execution starts in Phase 0 with coordinator P00, followed immediately by parallel spikes P01, P02, and P05; P03 takes the next free slot, while P04 waits on the concrete authentication paths established by P02 and P03 (`planning/kickoff.md`). Coordinator G0 acceptance is required before starting P06 production foundations.

07 · Provisional Performance Targets

Local responsiveness budgets separated from provider inference latency

To keep everyday usage snappy, UCLI budgets local CLI and supervisor overhead separately from upstream model generation time (`P30`, `docs/verification.md`). All values below are provisional p95 targets—none have been measured yet. Verification requires 30 cold and 100 warm benchmark runs on packaged Windows x64, macOS ARM64, and Linux x64 builds.

Operation / Resource Provisional Target Measurement Scope & Boundary
Help, version & shell completion p95 ≤ 100 ms Packaged binary cold/warm local CLI invocation (`P10`).
Cached model & task lists p95 ≤ 150 ms Local SQLite/cache read (`ucli models`, `ucli tasks`) without live network poll.
Cached interactive home launch p95 ≤ 250 ms Prompt ready with visible model/account/effort controls (`P11`).
Effective-setting resolution p95 ≤ 25 ms Typed config/flag/preset resolution (`P07`), excluding OS secret retrieval.
Added foreground wrapper overhead p95 ≤ 150 ms Cold UCLI with healthy local credentials; added startup overhead over matching direct launch, with provider latency reported separately.
Start through warm supervisor p95 ≤ 75 ms 75 ms added over matching direct launch; authenticated local IPC and the same resolved request.
First user-visible feedback p95 ≤ 100 ms Acknowledgement from command submission to initial status indicator.
Stream-to-display latency p95 ≤ 25 ms Adapter event receipt to terminal render without tearing scrollback (`P09`, `P11`).
Cancellation acknowledgment p95 ≤ 100 ms User cancel signal to local UI confirmation and state transition (`P23`); local acknowledgement only, not proof provider work has stopped.
Cooperative fixture stop ≤ 2 s Graceful child tree shutdown in controlled adapter fixture tests (`P09`).
Idle supervisor footprint < 75 MB · < 0.5% core Steady-state memory and CPU with zero active tasks (`P20`, `P30`).

Open decisions reserved for owner review

Routine implementation choices stay inside work packages, while concrete experience and boundary tradeoffs come back to the project owner at phase gates:

  • Core stack confirmation (`P01`): Accept the provisional Go binary only after packaged process, PTY, and startup spikes pass on Windows, macOS, and Linux.
  • Second daily-use runtime (`P03`): Confirm Antigravity (`agy`) vs. Meta Muse Code fallback or authorized Claude API path based on lifecycle and UX fit.
  • Provider account isolation & authorization (`P04`, `P15`): Approve only auth modes proven not to clobber shared native logins or violate provider terms (`OAI-03`, `CLA-03`).
  • Effort vocabulary mapping (`P07`, `P16`): Review how UCLI effort presets map onto provider-specific reasoning controls without implying identical compute budgets.
  • GitHub App vs. OAuth client (`P28`): Choose the device/OAuth registration path (`GIT-01`) for syncing identity and non-secret connection metadata.
  • Keychain & headless fallback (`P15`): Decide fallback behavior when an OS secret store is locked or unavailable in headless sessions.
  • Packaging & update channel (`P29`): Select the distribution and rollback mechanism for all three target platforms.
